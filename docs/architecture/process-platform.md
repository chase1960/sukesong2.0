# 流程产品分层与执行边界

> **文档状态：CURRENT（产品分层与接口边界；不是全功能已完成声明）**
> 最新完成度和缺口见 [当前进展](../../当前进展.md)。完整交互要求见 [设计器 spec](../standards/workflow-designer.md)。

## 1. 设计、办理、实例分开

| 层级 | 谁使用 | 职责 |
|---|---|---|
| 设计器 | 管理员、实施人员 | 配置图、表单、映射、参与人；校验、测试、发布 |
| 待办 / 流程中心 | 员工 | 汇总待我处理、我发起、已完成、抄送等事项 |
| 流程实例 | 具体办理人 | 看业务材料，执行当前允许动作，查时间线和异常 |

应用是业务一级入口。发起动作可以在应用首页、记录详情或全局可发起目录；不是所有流程都从待办页上传文件。自动触发属于另有明确输入、权限、幂等和失败策略的能力，不因模板存在就视为已支持。

## 2. 架构边界

- 原 shangshu-web 是唯一产品壳。Frappe Desk 的 /app 页面仅作内部运维和历史验证，不作为新业务产品入口。
- Frappe 提供对象、持久化、权限等基础；shangshu_core 通过版本化公共 API 管理尚书流程定义、发布版本、实例、动作及审计。
- Node 提供 BFF 与 AI/OCR/外部集成，不建立第二套流程事实权威。业务域注册自己的对象、动作与模板。
- 画布是可替换的编辑组件，不是流程运行引擎；不再要求嵌入 Frappe 原生 Workflow Builder，也不把组件私有 JSON 当公共协议。
- 公共调用与兼容性以 [public API v1](../guides/public-api-v1.md) 和 [内核基线](./kernel-baseline.md) 为准。行业代码不依赖 core 私有模块。

## 3. 使用端要求

待办列表展示事项、申请人、关键字段、当前阶段和更新时间，点击进入实例，不跳设计器。各视图必须按当前用户权限查询；未实现的抄送、异常等能力不能显示假成功。

实例围绕当前工作组织：业务表单、原始附件、当前允许动作、办理意见、状态、时间线和错误。拒绝、补充、重提等操作以已发布定义和当前授权为准，不让前端自行推导批准路径。

长期目标是通用元数据生成办理界面，避免每个流程复制一套页面；具体动态表单和高级办理能力是否已实现，查看根目录当前进展，不从此规范推断。

## 4. 设计与发布要求

设计端保持流程图、表单、数据流转、办理权限、发布测试五个工作视图。图表达顺序与分支，配置面板解释字段来源、动作和参与人。

保存草稿、结构校验、路径模拟、发布、真实执行是不同操作。任何完成声明必须说明验证了哪一层；模拟通过不等于动作真的执行。已发布版本不可覆盖，既有实例不得随新草稿漂移。

设计 schema、AI 提案和运行 schema 必须有明确映射；服务端不支持的节点或条件不因界面能画出就变成合法执行能力。新增公共语义必须单独提出兼容变更。

## 5. AI 治理

元数据使工具生成更容易，但不会天然产生安全、易用的工具。工具必须有稳定 ID/版本、输入输出、权限、effect、确认、幂等、失败和审计策略。

- 设计端：读取当前定义和合法资源，提出结构化变更，人工确认后进入草稿与测试，不直接覆盖发布版本。
- 运行端：按用户、业务记录、领域与节点裁剪工具；查询、材料处理和建议不等于获得写权限。
- 写动作：进入受管 Action 与确认审计；财务等不可逆操作不能交给模型直接写。
- 数字员工：复用同一能力和权限机制，不另造无限制执行通道；持久员工能力仍按专项计划验证。

## 6. 验收范围

每个具体交付应声明支持的节点、条件、表单、动作和异常范围，并用同一业务图验证：真实多角色办理、权限拒绝、分支边界、确认、重试幂等、版本隔离、运行轨迹和界面可用性。不能用 Administrator 串行探针替代全部角色或条件验收。

9 月 9 日的条件执行缺口以 [探针报告](../reports/2026-09/digital-employee-feasibility-probe.md) 为据；修复必须补真实运行回归，不改写旧验收结论冒充新能力完成。
