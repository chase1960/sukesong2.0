## 1. 唯一近期目标

在 `fast` 上形成一个“可扩展内核开发基线”，使知识产权行业工程师能够在独立分支内开发对象、页面、动作、流程、权限和 AI 能力，并满足：

1. 正常行业功能不修改关键内核代码。
2. 行业实现从第一天采用未来插件的目录、命名空间、manifest、迁移和公开接口边界。
3. `fast` 后续维护内核、修复缺陷或升级依赖时，可以持续合入行业分支，冲突集中在版本化公共接口而不是散落全仓库。
4. 后续继续优化流程图、表单和页面设计体验时，不改变已经发布的定义格式与运行语义。
5. 财务与知识产权两个真实领域共同证明扩展边界成立；不再制造抽象“示例域”。
6. 未来正式插件化主要补安装、依赖、签名和生命周期，不搬迁或重写行业业务逻辑。

这里冻结的是**公共协议与运行语义**，不是承诺永远不修改任何内核文件。安全、性能、缺陷和新公共能力仍可进入内核，但必须遵守兼容规则与 `CORE-CANDIDATE` 审核流程。

## 2. 本轮明确不追求什么

下列能力不是交付行业开发基线的前置条件：

- 完整页面拖拽设计器、任意布局或所有低代码组件。
- 工作流设计器的会签、委托、转交等全部高级交互。
- 应用市场、在线安装、第三方任意代码加载、签名与计费。
- 多企业 SaaS；当前继续一企业一部署，但公共协议保留 `enterprise_id`。
- 为了“看起来统一”重画尚书侧栏、登录页、消息或任务。

设计器只需能创建、编辑、校验、发布和测试公共流程定义。设计器 DOM、CSS、画布库和交互可以继续迭代，但不得成为运行时依赖。

## 4. 目标分层与所有权

```text
shangshu-web
  产品壳 + 公共组件 + 受管扩展插槽
        ↓ 只调用版本化 BFF 契约
Node BFF
  会话桥 + API 聚合 + AI/OCR/外部服务适配
        ↓ 只调用 shangshu_core.public_api v1
shangshu_core
  身份/权限/对象/动作/事件/流程/审计公共运行时
        ↓ 由 manifest + contribution 注册
业务领域 App
  finance / ip / future domains
```

### 4.1 `shangshu_core` 拥有

- 不可变身份、企业上下文、组织/角色基础和授权判定入口。
- 对象/字段定义协议和受权限控制的数据访问接口。
- Action 注册、执行、确认、幂等、重试、错误与审计。
- 版本化事件发布/订阅协议和投递审计。
- 流程定义、不可变版本、实例、节点执行、异常和运行时状态机。
- AI Tool 目录裁剪、调用政策、确认和执行审计。
- 文件引用、通知、调度、密钥等平台服务的接口；实现可逐步补齐。
- 领域注册、资源所有权、启停、贡献聚合、兼容与冲突检查。

### 4.2 Node BFF 拥有

- 浏览器到 Frappe 的同源会话/CSRF/错误映射，不成为第二身份权威。
- AI 模型、OCR 与外部系统适配；不得保存同一业务事实的第二份权威数据。
- 只按公共契约聚合领域资源；新增领域不得增加一组硬编码 `/finance/*` 式公共路由。
- 消息、任务等尚未迁移能力的兼容适配，并明确事实权威和退役路径。

### 4.3 业务领域拥有

- 自己命名空间内的 DocType、业务页面、动作、流程、角色补充和迁移。
- 自己的业务不变量、领域服务、AI 工具投影和外部服务声明。
- 自己的数据；跨域只能走公共 Action、Service 或 Event。

### 4.4 设计器拥有

- 将管理员操作转换为公共定义草稿与结构化 diff。
- 调用公共校验、模拟、发布接口。
- 展示运行时返回的错误、版本和测试证据。

设计器不拥有流程状态机、权限判定、动作执行或数据写入语义；不得将画布私有 JSON 直接作为不可替换的运行权威。

## 5. `shangshu_core.public_api` v1 目标协议

K1 必须建立单一公共包/模块入口。业务 App 不再直接导入 `runtime.py`、`domains.py`、`identity.py`、`database.py`、`immutable.py` 等私有实现。具体内部文件可重构，但下列能力及语义必须稳定。

### 5.1 公共上下文与身份

- `get_request_context()`：返回 `identity_id`、`enterprise_id`、用户、角色、能力和请求追踪 ID。
- `require_capability(capability, resource=None)`：统一授权入口。
- 不以可改名 email 作为永久外键；外部引用使用 `Shangshu Identity.identity_id`。
- Frappe 模式不可用时 fail closed，不静默回退 Node 用户库。

### 5.2 对象与数据

- `ObjectDefinition`/`FieldDefinition` 使用稳定命名空间 ID、schema 版本、owner 和权限声明。
- 提供受控 `query/get/create/update/propose`；禁止领域直接拼其他域 SQL 或更新其他域 DocType。
- 并发写使用版本/时间戳前置条件；高风险写入必须确认、幂等和审计。
- 记账与审计对象继续 append-only；纠错用反向记录，不覆盖历史。

### 5.3 Action

- Action 必须声明 `id/version/owner/effect/input_schema/output_schema/roles_or_capabilities/confirmation/idempotency/timeout/retry/audit`。
- 注册重复默认失败；同一 `id+version` 内容不得漂移。
- 领域只能通过公共 executor 注册与调用；不能把 Python 路径直接暴露给浏览器或 AI。
- 破坏性、高风险或账务动作必须由内核强制确认，不依赖页面自觉。

### 5.4 Event

- 事件 ID、版本、owner、payload schema、数据敏感级别和投递策略必须声明。
- 发布与订阅均记录审计；消费者必须幂等。
- 事件版本新增字段只能向后兼容；破坏性变更发布新 major/event ID。
- 禁止通过事件绕过 Action 权限或直接传递密钥、完整敏感文档。

### 5.5 Process Runtime

- `ProcessDefinition` 草稿与 `ProcessDefinitionVersion` 不可变发布版本分离。
- 实例永久绑定定义版本、enterprise、business reference 和发起身份。
- 节点只引用版本化 Action/Tool/子流程和结构化条件，不引用设计器 DOM 或临时函数。
- 对外稳定操作至少包括：创建/保存草稿、校验、模拟、发布、发起、查询实例、领取/完成人工任务、回放和异常处理。
- 流程定义格式升级必须提供 migration；旧实例继续按原版本运行。

### 5.6 权限

- 统一表达平台能力、对象记录范围、字段读写、流程参与人和动作权限。
- 页面可隐藏入口，但服务端必须重新判定；前端可见性不构成授权。
- 跨域调用以调用者身份和目标接口权限重新授权，不继承源领域的内部特权。

### 5.7 AI Tool

- Tool 是 Action 的受管投影，不是任意函数暴露。
- 必须声明输入/输出 schema、effect、候选范围、确认策略、超时、重试、敏感字段和审计。
- 工具目录按企业、已启用领域、当前用户权限和业务上下文裁剪。
- AI 只能产生提案；实际写入由公共 Action 执行并再次确认与授权。

### 5.8 领域与前端贡献

- manifest/贡献包含稳定 ID、版本、`platform_api` 范围、依赖、冲突、对象、页面、数据集、流程、Action、Tool、角色和迁移。
- 每个资源必须有唯一 owner；重复注册失败，禁止后加载覆盖。
- 页面只注册到平台插槽并使用平台令牌/控件；不得复制产品壳、登录、确认卡或权限实现。
- 领域专用 BFF 只能作为明确命名空间扩展；公共应用、数据、流程和 AI 页面只能消费聚合契约。

### 5.9 审计、错误与可观测性

- 公共写入统一记录 actor、enterprise、request/correlation ID、资源、输入摘要、结果、确认和幂等键。
- 公共错误具有稳定 `code`、用户中文说明、是否可重试和追踪 ID；不能依赖异常文案做程序判断。
- 敏感字段在日志、AI 上下文和审计摘要中按 schema 脱敏。

## 6. 版本与兼容规则

1. 平台公共协议采用 SemVer；首个交付基线为 `platform_api 1.x`。
2. 同 major 内允许增加可选字段、接口和枚举扩展，不删除字段、不改变既有默认语义。
3. 删除、重命名、权限收紧导致既有调用失败、状态机改变或 schema 不兼容必须升 major。
4. manifest 明确兼容范围；安装/启动前检查，不兼容时阻断并说明依赖链。
5. 废弃接口至少保留一个已发布 minor 周期，记录 warning、替代方案和删除版本。
6. 发布定义和历史事件 payload 不原地改写；通过迁移副本或新版本演进。
7. K1 起为公共 API 保存机器可读 contract snapshot；PR 比较 snapshot，潜在破坏变更必须失败并进入审核。

## 7. 行业代码从现在到插件化的形态

知识产权域当前可以直接随系统部署，不等待插件安装器，但必须保持：

```text
frappe_apps/shangshu_ip/
  shangshu-plugin.yml
  objects/
  actions/
  workflows/
  permissions/
  migrations/
  tests/
shangshu-server/src/domains/ip/
shangshu-web/js/domains/ip/
shangshu-web/css/domains/ip/
docs/domains/ip/
```

现在与未来插件的差异只能是安装/升级/卸载/签名机制，不能是业务代码所在位置或调用方式。业务页面、服务、流程和数据不得先散落到 core，等以后再“搬成插件”。

## 8. 修改边界与 `CORE-CANDIDATE`

### 8.1 行业开发默认允许

- 自己领域目录、DocType、页面、流程、动作、工具、迁移和测试。
- 通过已经冻结的注册入口增加 manifest/贡献。
- 只使用 `shangshu_core.public_api` 和版本化 BFF/前端插槽。

### 8.2 必须拆分并审核

- 修改 `shangshu_core`、公共 BFF、身份权限、流程运行时、公共组件或部署基线。
- 增加新的跨域公共能力、改变公共 schema 或运行语义。
- 扩大领域边界 allowlist、关闭兼容检查或修改公共 API snapshot。

审核材料必须包含业务场景、为何现有接口不足、拟议公共接口、兼容影响、安全影响、迁移和测试。通过后先独立进入 `fast`，再由 `fast` 合入行业分支。

### 8.3 永久禁止

- 行业代码直接更新其他领域表/DocType 或导入其他领域私有模块。
- 修改已经执行的历史 migration/patch；只能追加迁移。
- 以复制公共身份、权限、文件、流程或确认实现绕开审核。
- 同一业务事实在 Node 与 Frappe 双写。
- 将任意 Python/JavaScript、SQL 或密钥暴露给页面/AI。
- 修改或部署冻结 demo。

## 9. 自动门禁必须证明什么

现有 `check-domain-boundary` 保留，并在 K1-K3 增加：

1. 路径/内容门禁：允许、需审核、禁止三类，覆盖未跟踪文件。
2. import 门禁：领域只能导入 `shangshu_core.public_api`；跨域私有导入失败。
3. manifest 门禁：schema、命名空间、依赖、资源 owner、重复注册和平台版本检查。
4. contract 门禁：公共 API snapshot 和 JSON schema 兼容比较。
5. migration 门禁：历史迁移不可改、破坏性 SQL 失败、重复 migrate 幂等。
6. 权限门禁：匿名、越权、跨企业/跨记录和停用领域路径必须拒绝。
7. 双域门禁：core-only、finance、ip、finance+ip 四种组合均能安装/启停/升级。
8. 运行时门禁：旧实例版本冻结、动作确认/幂等/审计、事件重复投递和失败恢复。

门禁失败不能通过删除测试、扩大 allowlist、改 snapshot 或把代码搬进 core 绕过。

## 10. 事实权威冻结

| 事实 | 当前/目标权威 | Node 的允许角色 |
|---|---|---|
| 身份、角色、会话 | Frappe + `Shangshu Identity` | 同源会话桥，不维护第二套平台账户 |
| 新平台对象与字段 | Frappe Meta/DocType，经 public API | 聚合/外部适配，不双写 |
| 流程定义、版本、实例、节点 | `shangshu_core` | BFF 与 AI/外部触发适配 |
| 财务业务与账本 | `shangshu_finance` | OCR/外部集成，不保存第二账本 |
| AI/OCR 模型调用 | Node infra | 结果经公共 Action 回写 Frappe |
| 消息、任务遗留 | 按现状逐项登记 | 兼容期可继续权威，迁移前不伪称统一 |

`shangshu_flow` 和旧 Node 模块必须在 K1 形成“继续使用 / 仅兼容 / 待迁移 / 可退役”逐项清单；没有迁移和回归证据前不删除，已确定新权威后也不得继续新增双写。

- 在 `industry/ip-fde` 以知识产权最小真实链注册对象、页面、动作、流程、权限和 AI 工具。
- 不追求完整知识产权产品，只验证正常行业开发面。
- 同时回归 finance，不修改其内部实现。

**门禁：** 知识产权最小链从创建记录到多角色流程完成；行业提交通过边界检查，关键内核 diff 为零。

### K3：兼容、升级与恢复门禁（已完成）

- 完成 manifest/依赖/所有权/contract/migration 自动检查。
- 验证空站安装、旧站升级、重复 migrate、备份恢复、重启恢复和旧实例版本冻结。
- 验证 core-only、finance、ip、finance+ip 四种组合。

**门禁：** 模拟一次 `fast` 内核升级合入行业分支，两个领域无需业务重写且所有契约测试通过。

### K4：行业开发基线交付（已完成并通过 RC3 公网复核）

- 发布可追溯内核版本/tag、支持矩阵、安装升级说明、公共 API 文档、变更与废弃记录。
- 将该基线合入行业分支，提供开发提示词/规则、CORE-CANDIDATE 模板和故障恢复说明。
- 明确未完成但不影响行业开发的设计器/页面体验事项。

**门禁：** 同事仅修改行业域即可完成绝大多数专用功能；未来插件化不搬业务代码，只补安装生命周期。

## 12. 每阶段强制执行规则

1. 原逐阶段等待规则已由用户明确覆盖：K2-K4 连续完成后统一验收；后续新阶段仍须先明确目标和边界。
2. 开工前必须说明本阶段是否触碰公共协议、数据迁移、前端壳和公网。
3. 不以文档、类型检查或单一测试代替真实契约/运行验证。
4. 不借内核任务顺手重做全局视觉；公共页面问题可以定点修复并单独说明。
5. 设计器改动必须证明不改变已发布定义和运行时语义。
6. 行业验证必须使用真实业务链和多角色权限，不用只有名称的空示例。
7. 所有变更写入当日 worklog；阶段状态只有在证据完整且用户确认后才更新。
8. 公网部署只在该阶段明确需要时执行，部署主测试实例前备份，冻结 demo 永不触碰。

## 13. 最终完成定义

只有同时满足以下事实，才能称为“可扩展内核开发基线完成”：

- 对象、Action、Event、Process、Permission、AI Tool 和领域贡献均有版本化 public API 与契约测试。
- finance 和 ip 不导入 core 私有实现，不直接修改其他域。
- 新领域注册不要求修改公共 BFF、全局前端或流程状态机。
- 设计器可替换/迭代而已发布定义与实例继续运行。
- 显式平台模式下身份和事实权威唯一，不静默回退或双写。
- 四种领域组合、安装升级、版本冻结、权限、幂等、审计和恢复测试通过。
- 一次真实内核升级可以合入行业分支而不重写行业功能。
- 有可追溯版本、兼容矩阵、升级说明、已知限制和审核流程。

上述证据已经齐全，因此当前基线允许行业工程师开工。后续页面与设计器改进不得借机改变 `platform_api 1.x` 语义；若行业需求暴露公共能力缺口，仍必须按 `CORE-CANDIDATE → fast → industry/<domain>` 处理。
