## 1. 结论

### 首要准则：快速、简洁、可用

在安全与兼容边界内，以最少必要概念、接口和代码完成真实业务链。优先复用现有公共能力，合并同权限的重复读取，抽取已出现的重复行为；不造万能接口、预设框架或两套编辑器。新增能力须说明用户价值、无法复用的原因和完整链验证方式。详细执行规则唯一维护于 [重构方案首要准则](../plans/2026-09-10-low-code-refactor-audit.md#0-首要设计与执行准则快速简洁可用)，本设计中的建议拆分不得凌驾于该准则。权限、幂等、版本冻结与数据恢复不能省。

### 2026-09-10 用户确认：域、应用、页面与流程的职责

新增首要原则：面向搭建者的抽象必须可见、可配置、可验证；对象、受管组件、业务模板和动作在既有应用工作面呈现，人工与 AI 共用能力，不另建平行管理平台。具体定义、模板版本边界、CRUD 与业务动作区别及分包验收唯一维护于 [专项首要准则第 8 条](../plans/2026-09-10-low-code-refactor-audit.md#0-首要设计与执行准则快速简洁可用)，不把抽象可视化解释为额外框架建设。

- 域负责业务事实、规则、动作和权限边界，不只是存储数据。
- 应用组织完整业务，总览、页面、办理入口与配置入口围绕应用展开；每个应用有一个明确维护归属。目标允许引用其他域公开能力，不表示共同拥有或复制对方资源。
- 页面承载列表、详情、表单和看板。工作流在应用中配置，编排域提供的动作与条件，页面绑定发起和人工办理，公共内核执行、授权、版本化与审计。
- 当前注册实现一个域可贡献多个应用，应用资源只从所属域选取。跨域应用引用、依赖版本、停用影响和跨域失败恢复仍待专项设计与验证，不能宣传已实现。
- 前端近期实施：保留原品牌和全局壳；应用入口先展示应用总览，选择应用后进入业务总览，并在当前应用进入配置。流程设计归入应用配置，不另列普通员工的全局设计入口；数据从应用进入，待办统一汇总跨应用事项。
- 总览须区分个人工作台、应用目录总览和应用业务总览；无真实指标来源不伪造经营指标。不得因跨域组合能力尚缺，就把技术域强制拆成用户必须往返的独立应用。
- 历史 S0–S5 顺序已退役；后续仅按 [专项第 10 节精简实施路线](../plans/2026-09-10-low-code-refactor-audit.md#10-精简后的唯一实施路线待确认未开工) 经用户确认逐包执行。本文概念模型不等于需要逐项建表/建接口，不能用历史授权自动启动后续实现。

尚书低代码平台不是“数据页 + 一张工作流画布”，而是让企业实施人员从一个业务目标出发，完整配置并发布一套可供员工使用的业务应用：

```text
创建应用
  → 定义数据
  → 设计页面和表单
  → 配置业务动作
  → 编排流程与自动化
  → 设置人员和权限
  → 测试
  → 发布
  → 员工在应用内使用
```

流程设计器只是“应用设计”的一个子模块。普通员工日常使用的是已发布应用、业务页面、表单、待办和流程实例，不是画布。

## 2. 当前产品为什么让第一次使用者无法理解

当前实现有真实底层能力，但缺少上层产品组织：

1. 只有全局“数据”和“工作流”，没有“我正在构建哪个应用”的上下文。
2. 唯一已发布流程是费用报销，点击发起后立即上传票据，容易误解为所有工作流都以上传文件开始。
3. 工作台卡片由财务域的 Python 贡献声明生成，管理员不能在界面中配置布局、数据源或动作。
4. “应用管理”只能启停领域并显示资源数量，不能展开查看应用包含哪些页面、数据、流程、动作和权限。
5. 已有五视图流程设计器，但表单、页面、数据视图和应用导航尚未形成同一套可配置设计器。
6. 没有首次使用向导，也没有“创建应用 → 发布 → 作为员工预览”的连续路径。

因此，当前版本可以证明领域契约、数据查询和流程运行能力，但不能称为完整、易用的低代码产品。

## 3. 用户与工作空间

### 3.1 普通员工

目标是完成业务，而不是理解元数据：

- 从工作台进入常用应用或待办；
- 在应用中浏览数据、填写表单、执行有权限的动作；
- 在流程中心集中查看待处理、我发起、已完成和抄送；
- 使用 AI 辅助查询、填写、解释和准备材料；
- 不看到对象 ID、字段 ID、ActionDef、Graph JSON 或发布技术版本号。

### 3.2 业务管理员与实施人员

目标是搭建和维护应用：

- 创建应用、对象、字段、页面、表单和视图；
- 配置流程、自动化、参与人、权限和应用导航；
- 使用样例数据测试并预览员工视角；
- 发布不可变版本，查看差异、依赖、运行情况并回滚到新版本；
- 让 AI 生成结构化设计提案，但必须人工确认。

### 3.3 平台管理员

目标是治理平台和安装的业务域：

- 管理身份、组织、角色、领域启停和健康；
- 审核插件权限、依赖、冲突、迁移和外部服务；
- 查看审计、失败任务和生产运行状态；
- 不参与普通应用的每一次页面编辑。

## 4. 完整产品信息架构

产品分为“使用端”和“设计管理端”，两者共享同一登录、数据、权限和发布版本。

### 4.1 普通使用端

| 一级入口 | 用户看到什么 | 不应该出现 |
|---|---|---|
| 工作台 | 我的待办、常用应用、快捷动作、最近记录、管理员发布的卡片 | 流程节点库、字段映射、内部对象 ID |
| 应用 | 当前企业已发布且本人有权使用的业务应用 | 未发布草稿、插件技术清单 |
| 流程中心 | 可发起、待我处理、我发起、已完成、抄送、异常 | 所有流程定义画布 |
| 任务 | 派发、反馈、验收和协作任务 | 业务流程定义配置 |
| 消息 | 会话、群组、业务事项引用和通知 | 第二套账号系统 |
| AI 助手 | 查询、解释、辅助填写、材料检查和待确认提案 | 任意数据库、代码和未授权工具 |

“数据”不再作为脱离应用的默认业务入口。全局数据目录可以保留给高级用户，用于跨应用搜索和管理员治理；普通员工主要在具体应用中使用列表、详情和表单。

### 4.2 设计与管理端

| 一级入口 | 子模块 |
|---|---|
| 应用设计 | 应用概览、数据、页面、表单、流程、自动化、权限、导航、发布 |
| 资源中心 | 对象、字段、ActionDef、ToolDef、事件、连接器、文件引用、公共组件 |
| 应用管理 | 已安装领域、启停、健康、版本、资源清单、依赖、权限和审计 |
| 企业设置 | 企业资料、组织、成员、角色、身份映射；当前单企业部署不伪造多企业 |
| 运行治理 | 失败实例、重试、超时、审计、队列、外部服务和健康检查 |

## 5. 应用是低代码平台的第一层容器

每个业务系统先表现为一个 `ApplicationDefinition`，例如：

- 费用管理；
- 知识产权案件管理；
- 文件管理；
- 供应商管理；
- 合同管理。

一个应用拥有：

```text
应用
├── 首页 / 工作台
├── 导航
├── 数据对象与关联
├── 列表、看板、日历等数据视图
├── 详情页与表单
├── 业务动作
├── 流程与自动化
├── 角色与权限
├── AI 能力
└── 草稿、测试与发布版本
```

### 5.1 应用中心

普通员工进入“应用”后看到应用卡片：名称、说明、图标、本人可用的主动作和最近记录。管理员可以切换到“设计模式”，查看草稿、错误和发布状态。

应用卡片点击后进入该应用首页，不跳到全局数据表或流程画布。

### 5.2 应用首页

应用首页由页面设计器发布，可包含：

- 快捷动作，例如“申请报销”；
- 待办列表，例如“待我审批”；
- 数据摘要，例如“本月报销金额”；
- 最近记录；
- 图表和状态分布；
- 说明、公告和帮助；
- AI 建议或异常提醒。

应用首页不是由插件随意写 HTML，也不是在 Python 中写死布局，而是保存为版本化的 `PageDefinition`。

## 6. 第一次创建应用的标准流程

新用户点击“新建应用”后进入向导，而不是直接看到空画布。

### 第一步：说明要解决的问题

填写：

- 应用名称；
- 业务目标；
- 谁使用；
- 主要记录是什么；
- 是否需要审批、文件、通知或外部系统。

可以让 AI 根据自然语言生成第一版结构，例如：

> 创建一个供应商准入应用。采购提交资料，财务检查账户，负责人终审，通过后进入供应商名录。

AI 返回对象、页面、表单、流程和角色提案，用户确认后生成草稿。

### 第二步：确认数据结构

以业务语言展示对象与字段，例如“供应商申请、供应商、联系人、银行账户”，而不是要求用户先理解 DocType。

### 第三步：生成默认页面

系统根据对象生成：

- 列表页；
- 新建/编辑表单；
- 详情页；
- 默认搜索、筛选和状态视图。

### 第四步：配置业务过程

用户选择是否需要流程，并先选触发方式，再进入画布：

- 点击按钮人工发起；
- 创建或更新记录时触发；
- 定时触发；
- 接收 Webhook/API 时触发；
- 收到消息或领域事件时触发；
- 上传文件后触发。

### 第五步：配置人员与权限

设置谁能进入应用、查看哪些记录、编辑哪些字段、执行哪些动作和办理哪些节点。

### 第六步：预览、测试和发布

用样例身份和样例数据预览员工、经理和管理员视角；所有检查通过后发布不可变版本。

## 7. 页面设计器

页面设计器负责应用首页、列表页、详情页和自定义业务页面，不与流程画布混在一起。

### 7.1 基本布局

```text
顶部：返回应用 / 页面名 / 设备预览 / 撤销重做 / 保存 / 预览
左侧：组件库与页面结构树
中部：页面画布
右侧：选中组件的属性、数据、动作和权限
底部：校验、数据预览、事件和 AI 变更提案
```

### 7.2 首批组件

| 类型 | 组件 |
|---|---|
| 布局 | 栅格、分栏、区块、标签页、抽屉、弹窗 |
| 内容 | 标题、文本、说明、图片、状态标签、统计数字 |
| 数据 | 表格、列表、卡片、看板、日历、详情、图表、时间线 |
| 表单 | 文本、数字、金额、日期、选择、关联、文件、子表、审批意见 |
| 动作 | 新建、编辑、提交、确认、流程发起、导入、导出、领域 ActionDef |
| 协作 | 评论、附件、关注、消息、任务、办理记录 |
| AI | AI 填写、摘要、材料检查、解释、生成待确认提案 |

首批不提供任意 HTML、JavaScript、SQL、Shell 或无限制 HTTP 组件。需要扩展时通过受管组件与 ActionDef 注册。

### 7.3 数据绑定

组件只能绑定：

- 当前业务对象；
- 已声明关联对象；
- 已注册数据集；
- 当前流程实例；
- 当前用户与企业上下文；
- 节点输出或受管服务结果。

所有绑定在服务端再次执行对象权限、记录权限和字段权限，不能只靠前端隐藏。

## 8. 表单设计器

表单设计与流程节点共用 `FormDefinition`，但一个流程可以引用不同表单版本：

- 发起表单；
- 员工补充材料表单；
- 经理审批表单；
- 财务复核表单；
- 只读归档表单。

可配置：字段分组、顺序、说明、必填、只读、隐藏、默认值、校验、条件显示、字段权限、关联选择和文件规则。

表单提交只调用已注册业务动作；高风险字段和写动作必须经过确认与审计。

## 9. 数据建模与数据视图

### 9.1 数据对象

对象设计器提供：

- 对象名称和业务说明；
- 字段及类型；
- 唯一约束、必填和默认值；
- 一对一、一对多、多对多关联；
- 状态字段和生命周期；
- 记录归属与权限字段；
- 不可变、append-only 和红冲策略；
- 导入、导出和保留策略。

内部 DocType/表名只在高级信息显示。

### 9.2 数据视图

同一对象可以发布多个 `ViewDefinition`：

- 表格；
- 卡片；
- 看板；
- 日历；
- 时间线；
- 图表；
- 保存的筛选视图。

视图配置列、排序、筛选、分组、聚合、主动作、行动作、权限和移动端显示方式。

## 10. 工作流与自动化的入口模型

不是所有流程入口都放在流程中心，也不是所有流程都需要人工入口。

### 10.1 四类入口

| 入口 | 例子 | 展示位置 |
|---|---|---|
| 应用主动作 | 申请报销、创建合同 | 应用首页、页面按钮 |
| 记录上下文动作 | 提交审批、申请归档 | 列表行、详情页、表单 |
| 全局可发起 | 请假、报销、用印 | 流程中心“可发起” |
| 自动触发 | 逾期检查、入库校验、Webhook | 无需普通用户入口，进入运行治理 |

同一流程可以同时声明多个合法入口，例如费用报销既能在费用应用首页发起，也能出现在流程中心；文件识别可以由上传动作自动触发，不必显示成独立流程卡片。

### 10.2 触发器

`TriggerDefinition` 至少支持：

- `manual.form`：人工填写表单；
- `manual.record_action`：对某条记录执行动作；
- `data.created / data.updated`：数据事件；
- `schedule`：定时；
- `webhook / api`：外部调用；
- `message / domain_event`：消息或领域事件；
- `file.received`：文件进入受管入口。

触发器必须声明输入 schema、权限、幂等键、速率限制、审计和失败策略。

### 10.3 流程设计器的位置

管理员从“应用设计 → 流程”进入设计器。设计器继续包含：

- 流程图；
- 表单；
- 数据流转；
- 办理权限；
- 发布测试。

流程图只负责编排节点和路径；入口、应用导航、页面布局和工作台卡片分别在对应设计模块配置。

## 11. 流程中心与实例办理

流程中心是跨应用的个人工作汇总，不是全部业务的唯一入口。

固定视图：

- 可发起；
- 待我处理；
- 我发起的；
- 已完成；
- 抄送我的；
- 异常与需要补充（按权限显示）。

流程实例页根据当前节点的表单、数据和动作自动生成，至少显示：

- 当前事项和业务数据；
- 现在需要完成什么；
- 当前节点与下一步；
- 可执行动作；
- 附件、评论和补充材料；
- AI 输入、输出、候选工具、实际工具和选择理由；
- 完整时间线和审计；
- 异常、重试、退回、重提和转交。

## 12. 工作台如何配置

### 12.1 四层配置来源

工作台由平台合并四层定义，优先级从低到高：

1. 平台默认：我的待办、最近应用、消息和任务；
2. 应用贡献：应用提供的可选组件，不直接占据全局布局；
3. 企业管理员发布：为角色或组织发布布局；
4. 用户个人调整：收藏、隐藏、排序和尺寸，不得突破权限。

插件或领域只能“注册可用组件”，不能直接修改所有用户的工作台。

### 12.2 工作台设计器

管理员进入“应用设计 → 首页”或“企业设置 → 工作台”配置：

- 选择组件；
- 绑定数据集或统计查询；
- 设置主动作和点击去向；
- 选择可见角色和记录范围；
- 调整桌面栅格和移动端顺序；
- 预览员工、经理和管理员视角；
- 保存草稿并发布。

首批工作台组件：

- 指标卡；
- 待办列表；
- 快捷动作；
- 最近记录；
- 应用入口；
- 状态分布；
- 图表；
- 公告；
- 异常提醒；
- AI 建议。

### 12.3 工作台数据契约

每个组件必须声明：

```ts
interface WidgetDefinition {
  id: string;
  type: string;
  title: string;
  data_source: DataSourceRef;
  query: DeclarativeQuery;
  action?: ActionRef;
  visibility: PermissionRule;
  refresh_policy: "manual" | "on_open" | "interval";
  responsive: ResponsiveLayout;
  empty_state: EmptyStateDefinition;
}
```

不允许组件直接保存任意 SQL、Python 路径或 URL。数据查询必须来自对象、数据集或受管 Provider，并在服务端执行权限裁剪。

## 13. AI 在完整低代码平台中的位置

AI 不是单独的聊天页面，也不能替代确定性设计器。

### 13.1 设计端 AI

每个设计步骤都提供上下文入口：

- 应用：根据需求生成应用结构；
- 数据：建议对象、字段、关系和校验；
- 页面：生成布局和组件绑定；
- 表单：生成分组、校验和节点表单；
- 流程：生成 GraphCommand、条件和异常路径；
- 权限：解释冲突和最小权限；
- 测试：生成样例数据与路径用例。

AI 输出结构化 diff，用户逐项接受、拒绝或修改；不直接覆盖已发布版本。

### 13.2 运行端 AI

AI 可以：

- 解释页面和当前步骤；
- 查询当前用户有权看到的数据；
- 从文件提取字段；
- 辅助填写和检查材料；
- 生成摘要、意见和异常处理建议；
- 创建待确认业务动作。

AI 只能调用平台投影的 ToolDef/ActionDef。工具目录由“已启用应用 + 当前用户 + 当前记录 + 当前流程节点”动态裁剪。写入、外发、审批、财务和不可逆动作必须确认。

## 14. 权威元数据模型

完整平台至少包含以下版本化定义：

| 定义 | 作用 |
|---|---|
| `ApplicationDefinition` | 应用名称、导航、首页、资源与发布状态 |
| `ObjectDefinition` | 对象、字段、关系、生命周期和数据策略 |
| `ViewDefinition` | 表格、卡片、看板、日历和查询视图 |
| `PageDefinition` | 页面结构、组件、数据绑定和响应式布局 |
| `FormDefinition` | 发起/编辑/办理表单和字段规则 |
| `ActionDefinition` | 稳定业务动作、schema、权限、确认、幂等和审计 |
| `ProcessDefinition` | 流程图、节点、连线、表单、映射和参与人 |
| `TriggerDefinition` | 人工、数据、定时、API、消息和文件触发 |
| `DashboardDefinition` | 企业、角色、应用和个人工作台布局 |
| `PermissionPolicy` | 应用、对象、记录、字段、动作和流程权限 |
| `ReleaseDefinition` | 一次应用发布冻结的全部资源版本和依赖 |

运行时只执行已发布版本；草稿设计不能影响线上员工。发布应用时冻结页面、表单、视图、流程、动作引用和权限依赖。

## 15. 草稿、测试与发布

所有设计资源统一使用：

```text
草稿 → 校验 → 预览 → 测试 → 发布 → 运行 → 新草稿版本
```

发布前必须检查：

- 对象和字段引用存在；
- 页面和表单绑定合法；
- 流程所有路径可达且有终态；
- 参与人和记录权限一致；
- ActionDef/ToolDef 已注册且版本兼容；
- 写操作确认、幂等、事务和审计齐全；
- 桌面和 390px 基础布局通过；
- 依赖应用已启用且健康；
- 旧实例继续绑定旧版本。

回滚不是覆盖历史版本，而是从历史发布复制出一个新的草稿并重新发布。

## 16. 应用与插件边界

- Frappe App/尚书插件注册对象类型、动作、工具、页面组件、领域数据集和种子模板。
- 企业实施人员使用这些受管资源组装具体应用，不修改 core。
- 插件资源必须命名空间化；重复注册失败；跨域只走公开 ActionDef、Service 或 Event。
- 插件可提供“费用管理模板”，但安装后由管理员选择是否创建应用、启用和发布。
- 插件不能直接改全局侧栏、工作台布局、登录页、权限核心或其他插件数据。

完整在线安装、签名和隔离仍按 P3 执行；本文先定义产品和元数据形状。

## 17. 费用管理作为第一个完整样例

### 17.1 员工使用视角

```text
应用 → 费用管理
├── 申请报销
├── 我的报销
├── 我的待办
├── 发票
└── 帮助
```

点击“申请报销”后进入发起表单。上传票据是表单字段和票据抽取步骤，不是整个低代码平台的默认工作流入口。

### 17.2 管理员设计视角

```text
应用设计 → 费用管理
├── 数据：发票、报销单、应付、会计分录、收付款流水
├── 页面：应用首页、报销列表、报销详情
├── 表单：申请、补充材料、经理审批、财务复核
├── 流程：费用报销与付款
├── 自动化：票据上传后识别、完成后通知
├── 权限：员工、经理、财务、出纳
└── 发布：预览、角色测试、版本和审计
```

### 17.3 流程入口

费用报销可以同时出现在：

- 费用管理首页“申请报销”；
- 流程中心“可发起”；
- AI 助手的“准备一份报销申请”提案。

票据识别子过程由文件上传事件触发，不单独占据普通员工的流程中心。

## 18. 首次使用与空状态

### 18.1 无应用状态

管理员看到：

- 创建第一个应用；
- 从可信模板开始；
- 让 AI 根据业务描述生成草稿；
- 安装或启用已有业务域。

普通员工看到：

- 当前企业尚未向你发布业务应用；
- 仍可进入任务、消息和已有待办；
- 联系管理员，不展示元数据设计入口。

### 18.2 新应用空状态

按照“数据 → 页面 → 流程 → 权限 → 发布”显示完成进度和下一步，不留下无解释空白画布。

### 18.3 引导模式

首次进入设计端提供可关闭的任务清单和业务预览，不用大段教程覆盖页面。每一步都能切换到“员工预览”。

## 20. 现有能力如何迁入新结构

| 现有能力 | 目标位置 | 处理方式 |
|---|---|---|
| 领域启停与贡献聚合 | 管理端“应用管理” | 保留，增加资源详情和依赖视图 |
| 财务五个数据集 | 费用管理应用“数据/页面” | 不删数据，改为应用内导航 |
| 费用流程与五视图设计器 | 费用管理应用“流程” | 保留 Graph/Runtime，接入应用上下文 |
| 全局流程中心 | 使用端“流程中心” | 保留个人汇总，不再承担全部入口 |
| 当前工作台 Provider 卡片 | 工作台可选组件 | 改成组件注册 + 页面配置，不再直接占位 |
| 消息、任务 | 使用端公共能力 | 保留现有页面结构 |
| AI 浮层 | 全局助手 + 设计上下文入口 | 保留壳，接正式 Frappe ToolDef 执行桥 |
| 应用管理资源数量 | 应用详情 | 展开显示页面、数据、流程、动作、工具、角色和版本 |
