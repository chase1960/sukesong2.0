# 尚书内核（shangshu_core）变更日志

> 状态：CURRENT。内核版本独立于产品版本（`shangshu-v*`）与行业版本（`shangshu-ip-*`）演进，
> 只记录**内核与公共协议**的变更；业务域（finance / files / mail / 行业域）的变更记录在各自域内。
> 版本规则见[内核交付手册](../../docs/guides/kernel-delivery.md)“内核版本管理”节；升号时本文件必须同步增节。

## 0.20.0 — 2026-10-30（PKG-134-T01，会话证据候选，公共 API 1.20.0）

- 服务端签发身份／企业绑定凭据；提案固定关联，确认后随原统一日志事务保存，拒绝或重复确认不增加执行日志。
- 新增有权限限制的会话动作窗口；BFF按可信日志锚点返回前后各4条用户消息及对应内部调用，聊天正文不复制进日志。
- 有界读取、聊天实体部分索引及日志索引；普通来源展示不额外加载消息窗口，超限明确标记。
- 新增可空字段需先 migrate；候选未合入或部署3850。旧基线类型错误和一个原目录测试断言未在本批修改。

## 0.19.0 — 2026-10-28（结构门挡、有限并行准入、日志按幂等键互斥；公共 API 1.19.0，候选未发布）

- **结构门挡持久化**：模型新增内部协调字段 `scope_fence`（结构工程恢复标识）与 `write_zone_certification`（范围认证依据），**普通字段 patch 不能改**；DDL 前排空并持久化门挡，断连/隐式提交也不能让普通写穿过；同 token 可续作，错 token 拒；定义变化撤销并行资格。
- **有限范围并行准入**：首版只对**直接 HTTP `platform.object.update_many@1.1.0`、已认证的纯数据库对象**尝试 App 共享锁 → Model 排他锁 → 原目标记录锁；同应用不同对象可并行，同对象仍串行。配置先普通快照再真实缓存预检，合格后才当前共享读并锁空范围；取得配置共享锁后有变化即整事务失效并拒绝，**不带共享锁退回粗锁，不做 S→X 升级**。
- **日志按幂等键互斥**：去掉全局写者锁与年度流水号锁；新动作日志 ID 为 `LOG-`+幂等键 SHA256；复用 tabSeries 每个动作键一行的原生互斥，marker 与日志/目标同事务；marker=0 只查旧流水，marker=1 按确定主键当前读，缺失或事实不符直接拒。
- **绑定与认证**：每次认证新 nonce；绑定身份增改删先撤销资格，解绑不自动重新认证；工作文件的原生保存纳入同一保护。
- **兼容影响**：公共协议升到 1.19.0（`contracts/platform-api-v1.json` 的 `api_version` 同步）。未装 `shangshu_flow` 的部署，`after_request` 钩子实情与审过的名单差一条 ⇒ 判「不一致」⇒ 并行路径从未打开（见下条修复）。
- **本轮集成修复**：① 写入范围按「**所属应用已安装**」计算审过的钩子名单（多出来的没审过的钩子照样退粗锁，安全性质不变）——修掉「并行写路径在任何部署上都从未被打开」；② 文件域伴随投影写**日期**时补上日期格式（否则存盘重载变序号数，带日期列的伴随表第一次接入必然失败）；③ 两处并发判据的夹具改为按产品口径准备（空白伴随工作文件；先删版本行再删文件）。
- **行业分支合并注意**：本批改 `write_zones.py`、`write_zone_*.py`、`unified_log.py`、`object_companions.py` 等公共面 ⇒ **CORE-CANDIDATE**，行业分支合 fast 后须复跑并发与日志判据。

## 0.18.0 — 2026-10-28（事务失败传播，公共 API 1.18.0，候选未发布）

- 真实死锁/锁超时不再被吞成成功：保原始数据库错误，父层两次 commit 均拒，完整 rollback 后才可重试；同键重试只成功一次。普通文件错误仍为 pending。
- 兼容影响：事务失败语义变严——原先被吞掉的失败现在会**如实报错**（调用方需按错误处理，不要当成成功）。

## 0.17.0 — 2026-10-28（原子动作包，公共 API 1.17.0，候选未发布）

- `platform.object.update_many` 与受管 companion write/undo 升至 1.1.0：一个注册动作只写一条统一成功日志，完整逐记录变更保留在包步骤；已登记子动作回执关联根日志，同键重试不重复落账。旧成功请求继续原守卫重放；旧包版本的新请求或失败重试须升级，原生对象 companion 保留原执行口径。
- 原子包显式声明版本与子动作名单，保留每层权限、规则、确认和并发闸；禁止独立迁移，捕获子异常也不得报包成功。受控资源回滚支持包内去重 checkpoint，补偿失败阻止提交。

- 公共查询动作 `platform.object.query` 升至1.2.0，接通可选 `fields/read_scope/include_definition`；动作范围仅允许原分页 `query`，字段和结果集授权沿原入口，保留1.1.0历史定义。manifest与贡献仍使用同一动作/工具ID，无新增资源或业务表。
- 日常受管读取禁止省略范围而隐式全表；内置导出、迁移、分析和恢复消费者改为显式全量用途。无权/失效不回退旧存储，升级须将本批消费者和文件适配器一起加载。
- 注册effect=read的服务可走GET并传递读取取消，保留原权限、schema和生命周期；写服务及动作继续POST确认/幂等/事务。
- 批量审计保持逐条完整日志；字段投影不缩减必要规则，原生Frappe保存可能物理更新完整目标行。
- `platform.object.update_many` 公共入口自带变更通知合批并返回真实处理结果；嵌套晋升批次仅由最外层发送，失败子批次恢复进入前的待通知状态，不提前投影部分写入。逐行规则、版本、审计及原事务边界不变。
- 无新增业务表、数据归属迁移或清除历史日志；验证结果见公共按需访问计划及当日worklog。未提交、未发布不代表fast已包含。

- 回退须保留新增字段与部分采用守卫，不能让旧内核把已采用项再次整包执行。不涉及归属迁移、晋升、员工授权或邮件发送。

## 0.7.0 — 2026-10-06（本地候选，未部署）

- 领域对象可显式声明 `native_table`，把**原生 DocType** 接入公共表格工作面（`platform.object.query` 列表、`platform.object.export` XLSX、`import_preview`/`import` 导入与单元格编辑），仍以原生 DocType 为唯一事实，不建镜像受管对象或行业专用导出器。

- 表格读取按声明字段与当前身份过滤；导出与导入沿用受管对象同一 XLSX 契约、5000 行/50 万单元格与 500 行/10MB 上限；导入保持单事务、多行任一失败整体回滚、取消/预检零写、重放不重复。未声明 `create_action` 的对象只做「匹配即更新」，未匹配行明确报错，不伪造新增。
- 写列与身份列分离：只有声明写 Action 实际接受的列可编辑/可导入修改，其余列（如主键、案号）只能作为导入匹配依据；未接受的字段一律拒绝，不静默丢弃。
- 已声明原生表格的数据集查询回执带上对象能力投影，公共表格工作面按同一入口挂载；未声明或无权对象不投影。`platform.object.update/create` 对原生对象按 `map` 组装载荷后经声明写 Action 执行，确认、幂等与审计不变（表格面与本域动作各留一条审计）。
- 仅新增可选声明与分派；受管对象路径与 `platform_api 1.9.0` 语义不变。前端表格工作面接受 `source==='native'` 对象并隐藏字段设计入口。回退时撤回领域声明即可，保留数据与审计。
